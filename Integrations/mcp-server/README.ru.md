# MCP-сервер для Smart Sprint Planner

[English version](./README.md)

Сервер [Model Context Protocol](https://modelcontextprotocol.io) даёт ИИ-агенту (Claude Code, Kilo Code, Cursor и любому другому MCP-клиенту) доступ к данным планера по проектам YouTrack: рабочий спринт и состав задач по ролям, история, ёмкость, календарь и отсутствия, релизы, напоминания. Под капотом — [внешний REST-контракт планера](../openapi-sprint.yaml) редакции 3.49.1; сервер не хранит состояние, не имеет своих учётных записей и не расширяет прав.

**Версия сервера 0.1.0 · совместим с планером ≥ 3.49.1** (проверяется инструментом обзора проекта).

## Модель доступа

- Сервер общий (один на команду или инстанс), запускается в контейнере и слушает HTTP.
- Каждый запрос к серверу несёт **личный постоянный токен YouTrack** вызывающего в заголовке `Authorization: Bearer …`. Сервер пересылает токен в YouTrack и забывает: не кэширует, не логирует, на диск не пишет. Запрос без заголовка получает 401 ещё до протокола MCP.
- Права — ровно права пользователя токена: чтение доступно любому участнику проекта, запись — по группам ролей планера в настройках проекта (редактор, распределяющий, управление настройками, планировочный менеджер, релиз-менеджер, релиз-инженер). Подробно — глава об интеграциях в документации планера.
- Опасных операций контракта (полная замена истории, календаря, отсутствий и релизов, блокировка спринтов, отключение планера, запись полей задач) у сервера нет вовсе.

## Запуск в контейнере

```bash
cd Integrations/mcp-server
cp .env.example .env        # задать YT_BASE_URL и MCP_ALLOWED_HOSTS
docker compose up -d --build
curl http://localhost:8085/healthz
```

Образ `node:24-alpine`, шага сборки нет — образ копирует исходники. Внутри контейнера сервер слушает `0.0.0.0:8085`; TLS-терминация — на прокси перед контейнером. В `.env` токенов нет — они у клиентов.

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `YT_BASE_URL` | адрес YouTrack без завершающего `/` (из контейнера к хосту — `http://host.docker.internal:8080`) | обязательна |
| `PLANNER_APP_ID` | имя приложения планера в адресе контракта | из сборки |
| `MCP_TRANSPORT` | `http` — общий сервер; `stdio` — локальный запуск для отладки (тогда обязателен `YT_TOKEN`) | `http` |
| `MCP_HOST`, `MCP_PORT` | адрес прослушивания | `127.0.0.1`, `8085` (в контейнере `0.0.0.0`) |
| `MCP_ALLOWED_HOSTS` | `host[:port]` через запятую — защита от DNS-rebinding | пусто (выключена) |
| `MCP_LANG` | язык описаний инструментов и текстов: `en` или `ru` | `en` |
| `PROJECT_ALLOWLIST` | ключи проектов через запятую; пусто — все | пусто |
| `READ_ONLY` | `1` — инструментов записи нет | `0` |
| `YT_TIMEOUT_MS` | таймаут запроса к YouTrack | `30000` |
| `LOG_LEVEL` | `error` / `info` / `debug` | `info` |

В режиме `http` переменная `YT_TOKEN` запрещена — сервер откажется стартовать: у общего сервера нет своего токена.

Журнал — stderr, JSON-строками: время, инструмент, ключ проекта, исход, код отказа, `cid`, длительность. Ни тел запросов, ни токенов, ни значений полей.

## Подключение клиента

Токен — постоянный токен пользователя YouTrack (профиль → Authentication → New token). Хранить его в защищённом хранилище клиента, не в теле промптов.

**Claude Code** — файл `.mcp.json` в каталоге проекта агента; значение из окружения подставляется при запуске:

```json
{
  "mcpServers": {
    "planner": {
      "type": "http",
      "url": "http://localhost:8085/mcp",
      "headers": { "Authorization": "Bearer ${YT_TOKEN}" }
    }
  }
}
```

Либо командой (токен попадёт в конфигурацию клиента открытым текстом):

```bash
claude mcp add --transport http planner http://localhost:8085/mcp --header "Authorization: Bearer <токен>"
```

**Kilo Code, Cursor и другие** — тип `streamable-http` (`http`), тот же адрес и тот же заголовок.

Первый вызов агента — `planner_get_project_overview`: версия планера и совместимость, настроен ли планер в проекте, активные роли, состояние рабочего слота. Памятка агенту — ресурс `planner://guide/quickstart` и поле `instructions` сервера.

## Инструменты

Единицы: трудозатраты и ресурсы — **минуты** (8 ч = 480), даты спринта и релизов — epoch-ms, отсутствия — `YYYY-MM-DD`. Коды ролей, статусов и типов — латинские (ресурс `planner://reference/enums`). Обязательный аргумент у всех — `projectKey`.

| Инструмент | Что делает | Роль |
|---|---|---|
| `planner_get_project_overview` | версия планера, `configured`, активные роли, шапка слота, блокировка спринтов, число релизов | участник проекта |
| `planner_get_sprint` | рабочий спринт и состав по ролям (фильтр роли, лимит, исключённые; настройки — по флагу) | участник |
| `planner_get_history` | снимки спринтов по ролям с фильтрами `sprintId`, `roleKey`, `status`; задачи — с `includeItems` | участник |
| `planner_get_capacity` | запись ёмкости спринта (участники, грейды, ставки, доли, база); архив — по флагу | участник |
| `planner_get_calendar` | производственный календарь (фильтр года) | участник |
| `planner_get_absences` | отсутствия (фильтр логина и периода) | участник |
| `planner_get_releases` | реестр релизов, права вызывающего, ревизия; архив — по флагу | участник |
| `planner_get_reminders` | напоминания, адресованные вызывающему; журнал — по флагу | участник |
| `planner_upload_draft` | залить черновик спринта целиком; занятый слот — отказ `slot_occupied` без `overwrite` | редактор |
| `planner_upsert_item` · `planner_remove_item` | добавить/изменить задачу роли · убрать задачу | редактор |
| `planner_patch_sprint` | изменить часть шапки спринта (название, даты, цель, ресурсы ролей) | редактор |
| `planner_assign_person` | назначить или снять исполнителя задачи, даты работы | распределяющий |
| `planner_upsert_absence` · `planner_remove_absence` | добавить/заменить · удалить отсутствие | управление настройками / планировочный менеджер |
| `planner_upsert_capacity_person` | добавить/изменить участника ёмкости | то же |
| `planner_upsert_release` · `planner_set_release_status` · `planner_update_release_issues` | создать/изменить релиз · сменить статус · добавить и убрать задачи | релиз-менеджер (инженер — следующий шаг статуса) |

Ревизии: `baseRev` передавать не обязательно — сервер читает текущую и один раз повторяет точечную операцию при конфликте; переданный `baseRev` используется как есть. Полная заливка черновика не повторяется никогда.

Отказ планера приходит ошибкой инструмента: код `reason`, что он значит и что делать (из реестра кодов), `cid` для поиска записи в журнале планера; платформенные 401 и 404 — своими формулировками. Ресурсы: `planner://contract/openapi`, `planner://contract/error-codes`, `planner://reference/roles`, `planner://reference/enums`, `planner://guide/quickstart`. Промпты-сценарии: заливка черновика, точечные изменения, ведение релизов.

## Разработка и проверка

```bash
npm install
npm test                                   # юниты и инварианты, без сети
npm run check-contract                     # копии контракта равны Integrations/
YT_BASE_URL=http://localhost:8080 YT_TOKEN=... npm run smoke -- <КЛЮЧ>    # контрактный смоук на тест-стенде
```

Смоук пишет данные точечными операциями и возвращает состояние; работает только против localhost. Через уже запущенный сервер — `npm run smoke -- <КЛЮЧ> --url http://localhost:8085/mcp`. Локальный запуск для MCP Inspector: `MCP_TRANSPORT=stdio YT_TOKEN=… YT_BASE_URL=… node src/index.js`.

Код одинаков для обеих сборок планера; отличия — только `src/branding.js` (имя приложения, название, язык по умолчанию), `package.json` и этот файл. Копии контракта и реестра кодов в `contract/` синхронизируются `npm run sync-contract`.

## Выпуск версий

Пакет публикует GitHub Actions (`.github/workflows/mcp-publish.yml`) по тегу вида `mcp-vX.Y.Z`, совпадающему с `version` в `package.json`: прогоняются тесты и сверка контракта, затем пакет уходит в npm через доверенную публикацию с аттестацией происхождения, а образ контейнера — в `ghcr.io/letsrollamigo/smart-sprint-planner-mcp` с тегами `X.Y.Z` и `latest`. Ручной запуск workflow по умолчанию делает пробный прогон без публикации. Релизный процесс самого планера реагирует только на теги `vX.Y.Z`.

## Ограничения первой версии

Нет ограниченных операций контракта, согласования спринта, утверждения ёмкости и фаз; нет удаления релиза (у планера нет точечной операции); нет OAuth и сессий — токен в заголовке каждого запроса; ресурсы только статические.
