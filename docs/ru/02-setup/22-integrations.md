# 22. Интеграции: внешний REST

**Необязательно.** Планер не делает исходящих запросов и не подключается к внешним системам сам. Интеграция идёт в одну сторону: внешняя система обращается к серверным эндпоинтам планера через REST YouTrack под сервисной учётной записью и её постоянным токеном. Типовые сценарии — внешний агент собирает черновик спринта и записывает его в рабочий слот проекта; агент точечно меняет состав задач, отсутствия или релизы; внешняя система читает историю спринтов и ёмкость.

## Контракт

Контракт — файл [`Integrations/openapi-sprint.yaml`](../../../Integrations/openapi-sprint.yaml) в репозитории (OpenAPI 3.1): 43 операции в восьми разделах — спринт, история, ёмкость, календарь и отсутствия, релизы, напоминания, блокировка спринтов, администрирование. Файл открывается в любом просмотрщике OpenAPI (Swagger UI, Redoc). Версия контракта равна версии планера и поднимается каждым выпуском.

Полная таблица кодов отказов — [`Integrations/ERROR_CODES.md`](../../../Integrations/ERROR_CODES.md); она собирается из кода сервера при выпуске.

В файле контракта адрес сервера по умолчанию — заглушка `https://youtrack.example.local`: подставьте адрес своего YouTrack в поле `baseUrl`, прежде чем нажимать «Try it out».

## Подготовка

1. **Сервисный пользователь YouTrack** — отдельная учётная запись, не живой человек; постоянный токен создаётся в её профиле. Один пользователь на проект, не один на все — так ограничивается радиус токена.
2. **Доступ к проекту** — сервисный пользователь должен видеть проект средствами YouTrack.
3. **Планер подключён к проекту** (глава 03) — иначе платформа ответит `404 HTTP handler not found` ещё до кода приложения.
4. **Группа управления настройками задана** (глава 04). Без неё любая запись вернёт `plugin_not_configured`; чтение при этом работает.
5. **Полномочие в планере** — группа сервисного пользователя отмечена в нужной колонке таблицы прав (глава 09). Для заливки черновика спринта — «Редактирование».
6. **Откройте планер в проекте один раз.** Запись по основному адресу сверяет группу управления настройками с её копией в данных проекта. Копия создаётся и обновляется, когда планер открывают на вкладке проекта либо сохраняют его настройки. Пока этого не сделали, запись по ключу проекта отвечает `plugin_not_configured`; после смены группы управления настройками планер в проекте нужно открыть ещё раз.
7. **Токен — только в защищённом хранилище учётных данных** интегрирующей системы, не в теле сценария и не в переменных окружения открытым текстом.

## Адреса

| | Адрес | Особенности |
|---|---|---|
| **Основной — по ключу проекта** | `{baseUrl}/api/extensionEndpoints/smart-sprint-planner/backend-global/{путь}?projectKey={КЛЮЧ}` | Читаемый ключ проекта. Право пользователя читать проект проверяется до полномочий планера; нет проекта и нет доступа — единый отказ `project_unavailable`. Зависит от шага 6. Если планер в проекте отключён — `planner_disabled` |
| Альтернативный — по внутреннему идентификатору | `{baseUrl}/api/admin/projects/{projectId}/extensionEndpoints/smart-sprint-planner/backend-project/{путь}` | `{projectId}` вида `0-9` (`GET {baseUrl}/api/admin/projects?fields=id,shortName`). От шага 6 не зависит. Тумблером «планер отключён» не закрывается |

Аутентификация — заголовок `Authorization: Bearer <постоянный токен>`. Полномочия и проверки данных на обоих адресах одинаковы.

## Кто что пишет

Чтение (все GET) доступно любому участнику проекта: полномочие планера не проверяется, достаточно токена и доступа к проекту. Следствие — любой участник проекта читает настройки планера, ставки, грейды и отсутствия сотрудников. Это принятая модель доверия.

| Полномочие (глава 09) | Что пишет |
|---|---|
| Редактирование | Спринт и состав задач: полная запись, `upsertItem`, `removeItem`, `patchSprint`; фазы; снимок истории |
| Валидация | Согласование спринта по роли; фазы; снимок истории; полная запись истории (ограниченная) |
| Исполнители и даты | Персональное распределение: `assignerSync`, `assignPerson`; запись полей задач (ограниченная) |
| Группа управления настройками | Ёмкость, календарь, отсутствия, релизы, отключение планера |
| Планировочные менеджеры | Ёмкость и отсутствия |
| Очистка истории | Очистка истории и восстановление из резервной копии (ограниченные). Не наследуется даже администратором |
| Релиз-менеджер | Релизы: все операции |
| Релиз-инженер | Релизы: только продвижение статуса на следующий шаг |
| Блокировка спринтов | Блокировка создания спринтов (ограниченная) |

Полномочия не наследуют друг друга. **Ограниченные операции** заменяют данные целиком, необратимы либо меняют режим работы проекта; в контракте они помечены «⚠». Не используйте их, если задача решается мелкими операциями.

Радиус сервисного токена шире заливки спринта: полномочие «Редактирование» допускает и запись назначенных планеру полей задач — потолком служат права YouTrack самого сервисного пользователя (сервер проверяет, что пользователь видит задачу и вправе менять поле). Выдавайте сценарию минимальное полномочие, держите группу сервисного пользователя отдельно от групп живых людей. Кто и когда изменил данные, штампует сервер по учётной записи вызывающего; значения из тела запроса игнорируются.

## Ответы

Платформа YouTrack не пробрасывает HTTP-статусы приложения: и успех, и прикладной отказ приходят как **HTTP 200**. Результат определяется только по телу ответа. Настоящие не-200 отдаёт сама платформа: **401** — токен отсутствует либо недействителен; **404** `HTTP handler not found` — неверный путь или имя приложения либо приложение не подключено к проекту.

- **Успех:** `{ "success": true, … }`. Незнакомые ключи ответа следует игнорировать — ответы могут расширяться.
- **Отказ:** `{ "success": false, "error": …, "reason": …, "cid": … }`.

| Ключ | Что это |
|---|---|
| `error` | Класс отказа: `Bad Request`, `Forbidden`, `rev_conflict`, `internal_error`. У отказов записи полей задач в `error` стоит сам код причины |
| `reason` | Машинный код причины — есть всегда. **Ветвиться следует по нему** |
| `cid` | Идентификатор запроса — есть всегда. По нему в журнале сервера находится единственная строка отказа: статус и код причины, без тела запроса |
| `rev` | Только у `rev_conflict`: текущая ревизия данных |
| `errors` | Только у `calendar_invalid`, `absences_invalid` и `phases_out_of_sprint:` — массив с местом каждой ошибки |

Код, который в таблице кодов оканчивается двоеточием, — префикс: сервер дописывает уточнение (`ops_field_required:roleKey`). Сравнивать по началу строки.

## Ревизии и `baseRev`

Спринт (`sprint._rev` в ответе чтения спринта; пустой слот — 0), история, релизы и отсутствия (ключ `rev` ответа соответствующего GET) пишутся только с числовым `baseRev`:

- нет `baseRev` — отказ `base_rev_required`, ничего не записано;
- ревизия разошлась — отказ `rev_conflict` с текущим `rev`: перечитать GET, применить изменение заново, повторить;
- успех — в ответе новая ревизия `rev`; следующую запись можно делать с ней, без повторного чтения.

Без ревизии по замыслу: ёмкость, календарь, напоминания, блокировка спринтов, отключение планера, очистка и восстановление истории.

## Пример: точечные изменения агентом

**Мелкие операции** — одиннадцать вариантов записи «одно изменение вместо полной замены» (параметр `action`): для агентов это основной способ менять данные. Агент добавляет задачу в роль и назначает исполнителя, не трогая остальной состав:

```
GET  sprint-data?projectKey=DEMO                   → sprint._rev = 25

POST sprint-data?projectKey=DEMO&action=upsertItem
{ "roleKey": "analysis",
  "item": { "issueId": "DEMO-101", "inclusionStatus": "INC_PLANNED", "estimate_analysis": 480 },
  "baseRev": 25 }
→ { "success": true, "rev": 26, "action": "upsertItem",
    "applied": { "roleKey": "analysis", "issueId": "DEMO-101", "created": true } }

POST sprint-data?projectKey=DEMO&action=assignPerson
{ "roleKey": "analysis", "issueId": "DEMO-101", "login": "ivanov", "baseRev": 26 }
→ { "success": true, "rev": 27, "historyRev": 12, "action": "assignPerson", … }
```

- Трудозатраты и ресурсы — **в минутах** (интерфейс показывает часы). Статусы — только латинские коды (`PLANNING`, `INC_PLANNED`).
- `upsertItem` — слияние: присланные ключи задачи обновляются, остальные сохраняются. Единственный обязательный ключ задачи — `issueId`: название, состояние и приоритет сервер наполняет сам по полям, настроенным в проекте.
- `assignPerson` работает, когда роль уже отправлена на согласование либо спринт запущен — иначе `role_record_not_found`; `login: null` снимает назначение.
- Полная запись `POST sprint-data` с телом `{sprint, roleItems, baseRev}` заменяет рабочий слот целиком — заливать черновик нужно **до** начала ручного планирования. Неизвестный ключ в теле — отказ `invalid_*_structure`.
- Те же правила — у отсутствий (`upsertAbsence`, `removeAbsence`), ёмкости (`upsertPerson`) и релизов (`upsertRelease`, `setReleaseStatus`, `addReleaseIssues`, `removeReleaseIssues`).

## Совместимость

Внешний контракт меняется **только добавлением**: ключи и пути, под которые написан сценарий, не переименуются и не исчезнут; новое приходит новыми ключами и новыми вариантами `action`. Обещание распространяется на то, что клиент присылает; состав ответов может расширяться. Гарантия держится автотестами в репозитории: контракт сверяется с белыми списками кода и с базовой линией ключей, перечень кодов отказов — с кодом сервера.

## MCP-сервер для ИИ-агентов

Для ИИ-агентов (Claude Code, Kilo Code, Cursor и других MCP-клиентов) в репозитории есть готовый [MCP-сервер](../../../Integrations/mcp-server/README.ru.md) поверх этого контракта: девятнадцать инструментов — восемь чтения и одиннадцать точечной записи (заливка черновика с защитой от затирания занятого слота, задачи, шапка спринта, назначения, отсутствия, участники ёмкости, релизы) — плюс справочные ресурсы и промпты-сценарии. Это общий HTTP-сервер в контейнере; каждый запрос несёт личный токен YouTrack вызывающего в заголовке `Authorization`, поэтому права — ровно права человека за агентом. Ограниченные операции этой главы сервер не выставляет вовсе.
