## 1. Введение

**Smart Sprint Planner** — плагин YouTrack для мультиролевого планирования спринта. Раздельный учёт ресурсов по 9 функциональным ролям, персональное распределение задач между исполнителями, immutable-снимки валидированных спринтов в истории и рабочие копии для безопасных правок валидированных снимков.

### Поддерживаемые роли

| Ключ | Роль |
|------|------|
| `analysis`     | Анализ |
| `testing`      | Тестирование |
| `devPlatform`  | Платформенная разработка *(маппится на 1С, SAP, Salesforce, low-code и т.д. через настройки плагина)* |
| `devBack`      | Разработка Back |
| `devFront`     | Разработка Front |
| `devIos`       | Разработка iOS |
| `devAndroid`   | Разработка Android |
| `devFs`        | Разработка FullStack |
| `devDb`        | Разработка СУБД |

Каждая активная роль получает подвкладку с независимым составом, ресурсом и историей.

### Архитектура виджета

Один виджет — **`ssp-main`** (extensionPoint `PROJECT_SETTINGS`). Содержит:

- **Шапка виджета** — общая для всех вкладок. Включает: селектор «Текущий спринт» (один на весь виджет), бейдж агрегированного статуса (минимальный из активных ролей: PLANNING < CONFIRMED < ALLOCATED), индикатор **«✏ Рабочая копия»** (если для выбранного спринта есть незавершённая правка) и кнопку **«➕ Новый спринт»** (v1.6.2 — единственный черновик на роль, автопереход в «Планирование → Роли»; см. §4.1). Смена спринта в шапке немедленно перерисовывает активную вкладку. Если выбран исторический спринт без своей рабочей копии — активная вкладка переходит в hybrid read-only режим.
- **Три верхние вкладки**: **«📋 Планирование»** (с двумя уровнями детализации — *«Аллокация общего ресурса»* и *«Распределение по исполнителям»*), **«📈 Диаграмма Ганта»** (per-role timeline) и **«🕑 История спринтов»**.
- **Кнопка ⚙ Настройки плагина** — overlay настроек (видна только участникам `settingsManagerGroup`).
- **Серверный черновик** — несохранённые правки debounced flush'ем сохраняются на бэкенд (`ssp_drafts`, per-user слоты), восстанавливаются после F5. Бейдж в шапке: `●  Несохранённые изменения` или `💾 Черновик сохранён HH:MM`.
- **Рабочие копии** — отдельная мутабельная сущность для правок валидированных снимков; базовый снимок остаётся неизменным.

### Жизненный цикл спринта

`PLANNING` → (Валидация) → `CONFIRMED` → (Распределение) → `ALLOCATED` → (Закрытие) → `FINISHED`.

В статусе `ALLOCATED` строки таблицы заблокированы для правок (защита персонального распределения). Чтобы менять — **«Открыть на правку»** в спойлере истории (см. §6).

## 2. Установка и первичная настройка

**Для Project / Global Admin:**

1. Загрузите zip плагина в YouTrack 2024.3+ (**Administration → Apps → Upload**).
2. **Project Settings → Apps → Smart Sprint Planner** → задайте **`settingsManagerGroup`** (имя группы YouTrack, которая управляет настройками плагина в этом проекте).
3. До установки `settingsManagerGroup` плагин в **read-only** режиме (deny-by-default — защита от подмены настроек на свежей установке).

**Для участника `settingsManagerGroup`:**

1. Откройте проект, разверните виджет **Smart Sprint Planner** в Project Settings.
2. Нажмите **⚙ Настройки плагина** в шапке.
3. Заполните настройки (см. §3) и сохраните.

После сохранения базовых настроек и активации хотя бы одной роли — виджет планирования становится функциональным.

## 3. Настройки плагина

Overlay открывается кнопкой **⚙ Настройки плагина**. Закрытие — **✕ Закрыть** или `Esc`. Структурирован в 5 секций (sticky-меню из chips):

### 3.1 Доступ и роли

- **`activeRoles`** — выбор активных функциональных ролей (галочки 9 ролей). Неактивные роли не получают подвкладок.
- **`validationGroups`** / **`editGroups`** / **`historyClearGroups`** — multi-select групп YouTrack для валидации спринта, редактирования состава и полной очистки истории соответственно.
- **`assignerGroups`** — multi-select групп для **assigner-роли**: права только на изменение исполнителя и start/end-дат на «Распределение по исполнителям» и в Ганте; нельзя править состав, ёмкость, статус. Иерархия: `editor ⊃ assigner ⊃ viewer`. Если пользователь не входит ни в одну группу → read-only (как viewer).

### 3.2 Маппинг полей YouTrack

Для каждой активной роли:

- **`fieldEst`** — поле оценки (например, `Estimation`).
- **`fieldFact`** — поле факта (`Spent time`).
- **`userField`** — поле исполнителя (`Assignee`, `Developer`, `Tester`).
- **Прямое редактирование** (`dynEditEnabled`, переименовано в v1.4.0 — было *Inline-редактирование*) — включает редактирование `State` / `System` / `Priority` / `XPriority` прямо из таблицы спринта с записью в YouTrack.
- Также: `fieldPriority`, `fieldXPriority`, `fieldState`, `fieldSystem`, `fieldSprint`, `fieldVersion`.

### 3.3 Нормативы расчёта

- **`nkcJanuary`** / **`nkcMay`** / **`nkcOther`** — норма часов (январь / май / прочие месяцы).
- **`rate`** — ставка.
- **`participation`** — % участия.
- **`kpe`** — коэффициент по грейдам (Стажёр / Джун / Мидл / Синьор).

### 3.4 Режимы планирования

- **`personalPlanningEnabled`** — активирует уровень **«Распределение по исполнителям»** на вкладке «Планирование».
- **`usePersonalForResource`** — auto-recalc ресурса роли из персонального распределения (требует `personalPlanningEnabled`).
- **`manualPersonalResource`** (v1.4.0) — при включении ячейка «Ресурс (ч)» по каждому исполнителю в «Распределении по исполнителям» становится числовым полем ввода, привязанным к `entry.manualResource`; авторасчёт `NKC × KPE × rate × participation` подавляется, а dropdown грейда становится информационным. Используйте, если team-lead задаёт capacity «сверху вниз» (фиксированные часы в неделю на человека), а не через KPE-коэффициенты. Требует `personalPlanningEnabled=true`; иначе чекбокс заблокирован.

### 3.5 Дифференцированный учёт трудозатрат (DTA)

Агрегирует **work items** задачи по типу и записывает результат в fact-поля по ролям. Например, все work items типа *Разработка*, списанные на задачу, суммируются в `factFrontend`; *Тестирование* — в `factQa`. Маппинг хранится на уровне проекта, generic по списку активных ролей, с проверкой «один тип → одна роль».

Workflow-rule (`workflow-dta-aggregation.js`) поставляется **внутри YT-app zip** и регистрируется автоматически при установке плагина — никакого отдельного workflow-архива и шага *Админ → Workflows → Import* не требуется. Чтобы включить DTA в проекте:

1. Установить YT-app zip через **Apps → Upload App** (один раз).
2. Открыть настройки плагина в проекте, перейти на chip **«Учёт трудозатрат»**, включить **«Включить дифференцированный учёт трудозатрат»**, добавить строки `тип work-item → роль`. Сохранить.

С этого момента каждое создание/изменение/удаление work-item на задачах этого проекта триггерит пересчёт. Неактивные роли в маппинге пропускаются с предупреждением. Типы вне маппинга игнорируются.

**Локализация**: workflow выдаёт `workflow.message` на языке пользователя (`currentUser.profile.locale.language`) с fallback на `ssp_settings.defaultLang` и затем на `en`.

### 3.6 Каскадная агрегация трудозатрат (parent ← child)

Два дополняющих друг друга workflow-правила поставляются внутри YT-app zip и агрегируют поля плана/факта по ролям вверх по настраиваемой иерархии задач. Оба выключены по умолчанию и настраиваются через chip **«Каскадная агрегация»** в настройках плагина.

- **`cascadeAggregationEnabled`** (`workflow-cascade-aggregation.js`) — при изменении plan/fact-поля на дочерней задаче правило идёт вверх по настроенной **родительской связи** (default *subtask of* / *parent for* — встроенная связь YouTrack «Subtask»), суммирует то же поле по всем sibling-детям parent'а и записывает результат в parent. Если parent — level-2 (story-like) и у него самого есть level-3 parent (epic-like), правило в том же проходе пересчитывает и grandparent'а. Максимум 2 уровня иерархии (`задача → level-2 → level-3`); более глубокая рекурсия не поддерживается. Список агрегируемых полей derived автоматически из существующего DTA-маппинга «Поля → Оценка/Факт» для active-ролей — отдельного whitelist'а полей не требуется. Запись идемпотентна (diff `cur !== target`), поэтому повторное срабатывание правила на parent безопасно.
- **`forbidContainerWorkItems`** (`workflow-forbid-container.js`) — если включено, `workflow.check(false, …)` отклоняет save, если пользователь пытается добавить или отредактировать workItem на контейнерной задаче (kind ∈ `cascadeLevel2Values` ∪ `cascadeLevel3Values`). Блокируются и `workItems.added`, и `editedWorkItems`. Сообщение об ошибке локализовано. Bypass-групп в v1.3.0 нет.

**Имя kind-поля** (default `Type`), **списки значений** для уровней 2 и 3 (defaults `Story` / `Epic`; comma-separated для multi-value bundle вроде `Story, Feature`), а также **оба направления имени parent-связи** настраиваются на уровне проекта.

**Зачем оба вместе?** Каскадная агрегация перезаписывает plan/fact-поля parent'а при любом изменении ребёнка. Если кто-то параллельно списывает трудозатраты прямо на story или epic — это прямое списание будет затёрто следующей агрегацией. Settings UI выдаёт non-blocking warning при опасной комбинации cascade=on + forbid=off — production-режим **оба включены**.

### 3.7 Прочее

- **Переключатель языка** (RU/EN) — дублирует селектор в шапке виджета.
- **`enableDebugLog`** — debug-режим серверных логов.
- **`hideDiagLogUi`** — скрывает блок диагностического лога из UI. События продолжают записываться в память и доступны через **«📥 Экспорт»** в txt-файл после снятия флага.

Все настройки сохраняются в backend (`ssp_settings`), валидируются жёстким whitelist'ом (`ALLOWED_SETTINGS_KEYS`).

## 4. Вкладка «Планирование»

Единая верхняя вкладка с переключателем уровня детализации **«Аллокация общего ресурса / Распределение по исполнителям»**. Активный уровень запоминается между сессиями (`ui.planningLevel`).

### 4.1 Уровень «Аллокация общего ресурса»

Список 9 ролей (с учётом `activeRoles`) в виде accordion-карточек:

- **Свёрнутая** карточка — мини-сводка: ресурс / Σ allocation / count tasks / индикатор ⚠ overlimit.
- **Раскрытая** карточка — полный editable-редактор состава, ресурсов и валидации: статус-бейдж, поля имени/дат спринта, ёмкость роли, таблица состава с подбором/очисткой/пересчётом, кнопка валидации, NKC-селектор. Все DOM-id уникальны (содержат roleKey) — несколько раскрытых карточек одновременно не конфликтуют.

Состояние раскрытия персистится в `ui.expandedRoles[]`. Под кнопкой раскрытия (▼/▶) — кнопка **«→ Открыть в режиме «Распределение по исполнителям»»** (синхронизирует `_lastActiveRole` и переключает уровень).

#### Сортировка в таблицах задач

В шапках таблиц состава колонки **ID / Priority / XPriority** кликабельны — клик меняет ключ сортировки. Иконка `↕` (серая) на неактивных колонках, `▼` (синяя) на активной. Повторный клик по активной колонке → сортировка off (порядок storage). Sort-key persist в `localStorage.ssp_sortKey`.

#### Создание нового спринта (v1.6.2)

Кнопка **«➕ Новый спринт»** в шапке — единственная точка входа для создания спринта:

- **Один черновик на роль.** Каждый клик переиспользует тот же незавершённый черновик, а не плодит новые — название черновика берётся из локализованного плейсхолдера *«Новый спринт (не сохранён)»* (15 локалей). Повторные клики перезаписывают тот же черновик, поэтому случайный двойной клик больше не засоряет селектор спринтов UID-подобными «призраками». Как только вы заполняете название + даты и нажимаете **«Сохранить параметры»**, черновик становится настоящим спринтом, а следующий клик **«➕ Новый спринт»** создаёт новый черновик.
- **Автопереход в «Планирование → Роли».** На какой бы вкладке вы ни находились (История, Гант, «Распределение по исполнителям», настройки плагина), клик автоматически переводит вас в *«Планирование → Распределение ресурсов»* — именно туда, где заполняется название, даты и состав спринта по ролям.
- **Обязательные название и даты при сохранении.** Клик **«Сохранить параметры»** при пустом названии, дате начала или дате окончания блокирует сохранение, показывает локализованный тоаст («Введите название спринта» / «Укажите дату начала» / «Укажите дату окончания») и фокусирует незаполненное поле. Это заменяет молчаливое сохранение пустого UID-именованного неудаляемого спринта, которое было до v1.6.2.

После сохранения спринт появляется в селекторе **«Текущий спринт»** под своим настоящим именем и готов к редактированию состава по ролям.

### 4.2 Уровень «Распределение по исполнителям»

Видим при `personalPlanningEnabled=true`. Сверху — селектор роли (`#planningRoleSel`); по умолчанию — `localStorage.ssp_lastActiveRole` или первая активная роль.

- **Empty-state с CTA**: для роли без `personalPlanning[roleKey]` — плашка «Для роли «{name}» ещё не подобраны исполнители» + кнопка **«➕ Подобрать исполнителей»**. Клик вызывает `doDistribCalc()` напрямую. `personalPlanning[roleKey]` создаётся только после явного клика — чистый storage без пустых конфигов.
- **Полный editable inline-редактор** для заполненных ролей: NKC-селектор (январь / май / прочие месяцы), totals (Общий ресурс / Остаток), кнопки **«Рассчитать ресурс»** / **«Сохранить параметры»** / **«Валидировать распределение»**, таблицы исполнителей и распределения задач — всё работает inline в `#planningPeopleContent`.
- **Индикатор режима ресурса** при `usePersonalForResource=false`: ✅ ОК / 🟡 недо-распределение / 🔴 перелимит — показывает разницу между ручным ресурсом роли и Σ людей.
- **Soft-warn confirm при смене роли с dirty-данными** — закрывает класс багов «тихая потеря `_distribPP` при смене роли».
- **Двусторонняя синхронизация с Гантом**: смена ассайни через `<select>` в таблице задач немедленно перекрашивает соответствующий бар в `#tab-gantt` (если вкладка видима). Кеш цвета `taskAssignments[issueId].ganttColor` инвалидируется на каждую запись. Если вкладка Гант не открыта — следующий `refreshGanttForCurrentSprint` подхватит свежий ассайни автоматически.
- **Кнопка «🔄 Обновить из задач»** (v1.4.0 — переименовано из *«Обновить из YouTrack»*) — bulk-fetch актуальных assignee из YouTrack для всех задач спринта (до 200 issueId за запрос через `POST /refresh-assignees`). Источник правды = YouTrack: если кто-то поменял assignee напрямую в задаче, эта кнопка приведёт `_currentRolePP.taskAssignments` в соответствие. Обновление видно в таблице сразу + перекрашивает Гант.
- **Auto-select спринта при переходе с уровня «Аллокация»** — при переключении на «Распределение по исполнителям» автоматически подхватывается спринт, активный на «Аллокации». Не нужно выбирать спринт повторно.
- **Динамический re-render саммари роли** — показатели в шапке блока роли (Ресурс / Σ Аллокация / Кол-во задач / overlimit) обновляются после каждого изменения assignee/grade/dates без переключения вкладок.
- **Колонка «Система» в таблице распределения задач** (v1.4.0) — read-only сортируемая колонка между «Аллокацией» и «Исполнителем», показывает `item.system` по каждой активной задаче. В цикл сортировки добавлен primary key `system` (asc, tie-breaker — XPriority). Колонка отображается всегда; для задач без значения System рендерится «—».
- **Ручной ввод ресурса по исполнителям** (v1.4.0) — при `manualPersonalResource=true` (см. §3.4) ячейка «Ресурс (ч)» в таблице исполнителей становится числовым полем ввода. И остаток у исполнителя, и тоталы по роли в реальном времени следуют за введённым значением; dropdown грейда перестаёт триггерить авторасчёт, но остаётся редактируемым для документирования.
- **Колонка «Аллокации по проектам» в таблице исполнителей** (v1.4.0) — автоматически показывается, когда настроено поле System (`fieldSystem`) и включён `personalPlanningEnabled`. В каждой строке — per-system breakdown «`система · часы · процент`», построенный из активных задач (PLANNED / UNPLANNED), назначенных на этого исполнителя, и сгруппированных по `item.system`. Задачи без системы попадают в «Вне проектов/систем» приглушённым курсивом; строки свыше 100 % ресурса исполнителя получают красную пометку `⚠`. Колонка обновляется автоматически после переназначения, ручных правок ресурса и изменений аллокаций.

### 4.3 Hybrid поведение для исторических спринтов

При выборе исторического спринта в шапке виджета:

- **Без активной собственной WC** — все input'ы в `#tab-planning` И `#tab-gantt` read-only (CSS-класс `.readonly-mode`); нужно «Открыть на правку» через спойлер истории.
- **С активной собственной WC** — read-only снимается автоматически, можно править как текущий спринт.

### 4.4 Cross-tab синхронизация

Если открыли виджет во второй вкладке браузера и начали править — индикатор `.widget-header__wc` в первой вкладке обновится без F5 (через `window.addEventListener('storage', ...)` с ключом `ssp:wc-touched:*`). Активная вкладка `#tab-gantt` тоже re-render'ится при изменении WC из другой вкладки.

## 5. Вкладка «Диаграмма Ганта»

Отдельная верхняя вкладка `#tab-gantt` с per-role timeline.

- **Селектор роли** (`#ganttRoleSel`) сверху — синхронизирован с `localStorage.ssp_lastActiveRole` (общий с уровнем «Распределение по исполнителям»). При смене роли в Ганте — следующий открытый «Распределение» подхватит ту же роль, и наоборот.
- **Кнопка «Обновить Гант»** — пере-рендер timeline по текущим данным. В hybrid read-only режиме скрыта.
- **Кнопка «🔄 Обновить из задач»** (v1.4.0 — переименовано) — pull актуальных assignee из YT для всех задач спринта (та же кнопка, что на «Распределении по исполнителям»; bulk fetch до 200 issueId за запрос).
- **Цвет бара = функция от ассайни**: фиксированная палитра 12 цветов через `assigneeColorOf(login, allLogins)` — round-robin по индексу логина в отсортированном списке роли. Тот же логин получает один и тот же цвет независимо от состава таблицы. Нераспределённые задачи (без assignee) — серые (`#9aa3ad`).
- **Single-click → реассайн**: одинарный клик по бару открывает модал `#reassignOverlay` со списком ассайни роли + опция «— Не назначен —». После «Применить» — `taskAssignments[issueId].assignee` обновляется И **значение записывается в YouTrack issue field** через `POST /update-issue-field`. Бар немедленно перекрашивается в новый цвет, dirty-флаг ставится. **Требует включённого inline-редактирования** (`dynEditEnabled=true` в Settings) — без него single-click показывает toast `ganttReassignDisabledByInlineEdit`. Логика: реассайн = YT writeback, не должен быть доступен в режиме «локальная правка только в плагине».
- **Double-click → локальная color-маркировка**: dblclick по бару переключает локальный color-override `taskAssignments[issueId].userColorOverride` по циклу `red → blue → null`. **Не требует inline-edit** — это локальная UI-маркировка без YT writeback. Полезно для подсветки задач (например, «требует обсуждения» = red, «готова к ревью» = blue). Persist в `personalPlanning`.
- **Двусторонняя синхронизация с уровнем «Распределение по исполнителям»**: реассайн через модал немедленно обновляет `<select>` в таблице задач (если уровень «Распределение» уже отрендерен). Невозможно создать рассинхрон между двумя представлениями.
- **Hybrid read-only режим**: при выборе исторического спринта без своей WC click блокируется через CSS `pointer-events:none` + проверка `_isEditor` / `.readonly-mode` в JS-handler'е (belt-and-suspenders).
- **Soft-warn confirm при смене роли с dirty-данными `_currentRoleGantt`** — защищает от потери незавершённых правок цветов.

**Совет**: если diagram пустая — проверьте, что у роли есть валидированный спринт (`CONFIRMED` или выше) и распределённые исполнители на уровне «Распределение по исполнителям».

## 6. Вкладка «История спринтов» и рабочие копии

Список snapshot'ов валидированных спринтов (по 10 на страницу, сортировка по `confirmedAt` desc). Каждый снимок — отдельный спойлер с метаданными (даты, статус, валидатор, остаток ресурса) и таблицей задач.

### Кнопки в спойлере

- **Excel** — экспорт спринта (xlsx с колонками задача / оценка / факт / ресурс / аллокация / итого).
- **✏ Открыть на правку** — создаёт рабочую копию (см. ниже). Видна для валидаторов; скрыта для `FINISHED`.
- **Завершить** — `ALLOCATED → FINISHED`. Необратимо.
- **🗑 Удалить** — удаление снимка (требуется подтверждение).
- **🗑 Очистить всю историю** — отдельная кнопка над списком; только участникам `historyClearGroups`.

### Рабочие копии

При клике **✏ Открыть на правку** базовый снимок не разрушается. Создаётся **рабочая копия** в `_workingDrafts['<sprintId>_<roleKey>']`:

1. **Баннер** в шапке планнера: «✏ Рабочая копия: {спринт} [{роль}] · базовый снимок от {дата}» с pill уровня ре-валидации (META / ALLOC / CONFIRM):
   - **META** (синий) — изменены только метаданные → статус сохранится.
   - **ALLOC** (оранжевый) — изменены аллокации / ресурс роли → `ALLOCATED → CONFIRMED`.
   - **CONFIRM** (красный) — изменён состав / inclusion / оценки → статус → `PLANNING`.
2. **Кнопки баннера**: **«Показать различия»** (diff added / removed / changed) и **«✕ Свернуть»** (working copy сохраняется, баннер скрывается, активный спринт восстанавливается).
3. **Pill «✏ Есть рабочая копия (от {who}, {when})»** в спойлере истории — рядом со status badge.

### Ре-валидация

Откройте working copy → внесите правки → нажмите **«✔ Валидировать»** на планнере. Уровень ре-валидации применяется автоматически:

- При расхождении базового снимка (другой валидатор перезаписал параллельно) — **модал «Конфликт версий»**: «Перезаписать своими / Скачать обе версии в Excel / Отменить».
- После коммита: working copy удаляется, в `snap.revisions[]` добавляется `{at, by, level}` (audit-trail, лимит 200 записей).

### Multi-tab

- Открытие своей working copy в новой вкладке → soft-warn модал «Открыто в другой вкладке» с выбором «Продолжить здесь / Открыть только для просмотра».
- Открытие чужой working copy → кнопка «Открыть на правку» disabled с tooltip «Уже редактирует {who}». Бэкенд блокирует take-over (HTTP 403 `not_owner`).

### Discard

Кнопка **«Отменить правку»** (только владельцу) в спойлере → двухступенчатый confirm → working copy удаляется, базовый снимок не пострадал.

### GC

Working copies со `updatedAt > 30 дней` или orphan (без базового снимка) удаляются один раз при загрузке плагина (lazy purge, без фоновых таймеров). Сводный toast: «Удалено старых рабочих копий: N».

### Экспорт

Кнопка **Excel** на каждом снимке экспортирует xlsx с колонками: задача, оценка, факт, ресурс, аллокация по выбранной роли + итого.

## 7. Роли, права, группы

| Группа | Что разрешает |
|--------|---------------|
| `settingsManagerGroup` (app-settings) | Управление настройками плагина (открытие overlay настроек). **Source of Truth** прав плагина. |
| `editGroups` (`ssp_settings`) | Редактирование `_sprint`, `_roleItems`, `_items` (sprint-data POST). Прямое редактирование YouTrack-полей. |
| `validationGroups` (`ssp_settings`) | Валидация спринта (`POST sprint-data?action=validate`); создание и коммит рабочих копий (`POST working-drafts`). |
| `historyClearGroups` (`ssp_settings`) | Полная очистка истории (`POST history?action=clear`). |
| `assignerGroups` (`ssp_settings`) | **Только** изменение исполнителя и start/end-дат на «Распределение по исполнителям» и в Ганте (через `action=assignerSync`). YT writeback только для assignee-полей через `POST /update-issue-field`. Не позволяет менять состав, ёмкость, статус. Иерархия: `editor ⊃ assigner ⊃ viewer`. |

**Серверная авторизация** (`backend-project.js`): `authzGuard(ctx, role)` в начале каждого endpoint'а. Клиент никогда не передаёт свои группы — сервер берёт из `ctx.currentUser.groups`. Deny-by-default: если `settingsManagerGroup` не задана в app-settings — все мутирующие endpoint'ы возвращают 403.

**Кросс-юзер защита working copies**: `editorLogin` всегда перезаписывается серверным `ctx.currentUser.login` (defense-in-depth). Take-over чужой working copy запрещён.

См. [SECURITY.ru.md](SECURITY.ru.md) для полной матрицы доступа.

## 9. Диагностика и FAQ

### Diag-панель

Внизу виджета — раскрывающаяся панель **«Диагностика»**. Логирует все API-запросы, ошибки, миграции данных, GC. Включает кнопку «Очистить лог». Полезна при сообщениях о багах — приложите содержимое лога.

В шапке панели — кнопка **«📥 Экспорт»**. Клик создаёт файл `ssp-diag-YYYYMMDD-HHMMSS.txt` (последние 100 строк лога). Приложите его к багрепорту.

Чтобы скрыть панель: **Settings → Прочее → «Скрыть панель диагностического лога из UI»**. Сохраните настройки. Блок исчезнет, но события продолжат записываться в память — экспорт через TXT работает после снятия флага.

### Серверный debug log

`enableDebugLog` в app-settings — включает `console.log` на стороне backend (`dlog`). По умолчанию выключен. Не логирует значения user input (только короткие маркеры).

### FAQ

**Q: Открыл спринт на правку из истории, но потом понял, что ничего менять не надо. Как вернуться?**
A: В баннере «✏ Рабочая копия...» в шапке планнера — кнопка **«✕ Свернуть»**. Working copy сохранится (можно вернуться позже через **«Продолжить правку»**). Если хотите удалить — в спойлере истории кнопка **«Отменить правку»** (двухступенчатый confirm, базовый снимок не пострадает).

**Q: Кто-то другой уже редактирует спринт. Как я могу его открыть?**
A: Никак, пока он не закроет working copy (либо не сделает discard, либо не закоммитит ре-валидацию, либо не пройдёт 30 дней — тогда GC удалит). При попытке клика — toast «Уже редактирует {логин}». Договоритесь напрямую.

**Q: Что произойдёт, если я просто закрою браузер во время правки working copy?**
A: Working copy сохраняется на бэкенд debounced flush'ем (300 мс). При следующей загрузке вы увидите её в спойлере с pill «Есть рабочая копия». Откройте «Продолжить правку».

**Q: Я изменил только название спринта — почему статус не упал?**
A: Это уровень `META_ONLY` — статус сохраняется. Изменения метаданных (имя / даты / Sprint / Version поля) не разрушают валидацию. В баннере pill будет синий **META**.

**Q: Я изменил аллокации в `ALLOCATED` спринте — статус сбросился до `CONFIRMED`. Почему?**
A: Это уровень `ALLOCATED_REVAL` — изменение аллокаций требует повторной валидации персонального распределения. Перейдите на уровень **«Распределение по исполнителям»** для нужной роли и нажмите **«Валидировать распределение»** снова.

**Q: Я добавил/удалил задачу в working copy — статус упал до `PLANNING`. Почему?**
A: Уровень `CONFIRMED_REVAL` — изменение состава задач требует прохождения всех этапов с начала: валидация состава (`PLANNING → CONFIRMED`), потом распределение (`CONFIRMED → ALLOCATED`).

**Q: При коммите working copy появился модал «Конфликт версий». Что делать?**
A: Кто-то другой переписал базовый снимок параллельно (например, сделал `Finish`-операцию или другую правку через свою working copy). Варианты: **«Перезаписать своими»** (ваши изменения станут текущими, чужие потеряются), **«Скачать обе версии в Excel»** (для merge вручную), **«Отменить»** (working copy сохранится — можете обсудить и решить).

**Q: Я в группе `assignerGroups`, но не могу изменить состав спринта. Это ошибка?**
A: Нет, это by design. Assigner-роль ограничена: можно менять **только исполнителя и start/end-даты** на «Распределение по исполнителям» и в Ганте. Изменение состава задач, ёмкости роли, статуса требует прав `editor` / `validator`. Иерархия: `editor ⊃ assigner ⊃ viewer`. Если нужны полные права — попросите settingsManager добавить вас в `editGroups`.
