Differentiated Time Accounting
When enabled, the bundled workflow rule aggregates issue work items by type and writes the result into per-role fact-fields according to the mapping below. Each work item type may be mapped to a single role only.
When enabled, the workflow emits per-role plan-vs-fact progress messages on each work-item logging: under 90% — informational ratio, 90-100% — warning that less than 10% of the plan remains, over 100% — overrun alert. The role label and advice text are localised. Disable this checkbox if you only need the silent fact-field aggregation.
Work item type (exact name) Role
A work item type cannot be mapped to two different roles. Remove the duplicate row before saving.
Cascade aggregation of work hours
When enabled, the bundled workflow rule sums per-role plan/fact fields (derived from DTA Fields → Estimate/Fact mapping) from child issues into their level-2/level-3 parents along the configured parent link. Hierarchy max 2 levels (task → level-2 → level-3).
When enabled, saves are rejected if a user tries to add or edit work items on issues whose kind matches a level-2 or level-3 container value. Time logging must happen on leaf child issues only.
⚠ Cascade is on while forbid is off: any direct work-item logged on a container issue will be overwritten by the next cascade aggregation. Enable «Forbid direct logging» to keep aggregated values consistent.
Leave empty if you only need 1-step aggregation (task → level-2). When set, cascade extends to level-3 (level-2 → level-3).
⚠ Level-2 and level-3 must not share a value — overlap is ambiguous and breaks aggregation.
Defaults match the built-in YouTrack «Subtask» link type (inward «subtask of», outward «parent for»). Override only if your project uses a custom relation. Both directions must be filled.
State rollup parent ← children
When enabled, the bundled workflow rule recomputes container State (Story / Epic) as the least-progressed state across child issues whenever any child State changes. Reuses the hierarchy config from «Cascade aggregation» above. Disable if you have custom state-propagation workflows.
⚠ Rollup needs hierarchy config from «Cascade aggregation» above (kind field + level-2 / level-3 values). Fill that section first.
Select states from the project bundle and order them from «least progressed» (Open / Backlog) at the top to «most progressed» (Done / Closed) at the bottom. The rollup picks the topmost state across all children. Minimum 2 states.
⚠ State order must contain at least 2 states.
When a container is already in any of these states, rollup will not change it back. Typically: Done, Cancelled. Leave empty to disable the guard (containers will follow children even after closing).
Containers won't drop below this state even if children would push them lower. Use to keep Epics out of «Backlog» once analysis has started.
v1.7.0 supports «min» only. «max» (any-progressed) and «mode» (majority) are reserved for future releases.
Forces a one-time recomputation across all level-2 / level-3 containers in this project. Use after enabling rollup for the first time or after a bulk state change. Cooldown: 60 seconds.
